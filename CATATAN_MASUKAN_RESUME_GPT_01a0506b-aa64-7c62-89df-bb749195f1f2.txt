RENCANA SKALABILITAS 1.000+ PEMBAYARAN
=====================================
Mekanisme retry saat ini aman sebagai jaring pengaman, tetapi belum optimal
untuk lonjakan 1.000 atau lebih pembayaran bersamaan. Pemrosesan satu koneksi
MikroTik per pelanggan dapat membebani router dan memperpanjang antrean.

Solusi pengembangan berikutnya:
1. Buat tabel payment_activation_queue dengan data ID transaksi, IDPEL,
   periode, server/router, status, jumlah percobaan, jadwal retry, pesan error,
   dan waktu aktivasi.
2. Gunakan unique key pada ID transaksi agar callback berulang tidak membuat
   pekerjaan aktivasi ganda.
3. Setelah transaksi berstatus BERHASIL, callback hanya mencatat pekerjaan ke
   antrean dan segera memberikan respons sukses kepada payment gateway.
4. Worker mengambil pekerjaan pending dan mengelompokkannya berdasarkan
   MikroTik. Satu koneksi router dipakai untuk memproses banyak pelanggan.
5. Ubah hanya pelanggan yang profilnya masih EXPIRED. Pelanggan dengan profil
   normal dilewati tanpa memutus sesi.
6. Setelah profil diubah, putus sesi PPPoE pelanggan terkait dan verifikasi
   bahwa profil paket normal sudah diterapkan.
7. Batasi paralelisme, misalnya maksimal lima router diproses bersamaan dan
   100-200 pelanggan per batch pada satu router.
8. Gunakan status antrean pending, processing, success, dan failed. Pekerjaan
   yang gagal dicoba ulang setelah 1, 2, 5, 10, lalu 30 menit.
9. Setelah melewati batas percobaan, pekerjaan ditandai failed dan tersedia
   untuk retry manual oleh admin.
10. Sediakan halaman monitoring yang menampilkan jumlah pending, processing,
    success, failed, durasi aktivasi, serta pesan kegagalan per pelanggan.
11. Pertahankan cron rekonsiliasi saat ini sebagai pengaman terakhir sampai
    worker antrean batch terbukti stabil.

Contoh kapasitas:
Jika 1.000 pelanggan tersebar pada 10 MikroTik, worker cukup membuka sekitar
10 koneksi router dan memproses pelanggan secara batch, bukan membuka 1.000
koneksi MikroTik secara terpisah.

SKENARIO 1 MIKROTIK UNTUK 1.000+ PELANGGAN
=========================================
Jika seluruh pelanggan berada pada satu MikroTik, beban aktivasi terkonsentrasi
pada router tersebut. Sistem tidak boleh membuka satu koneksi API untuk setiap
pelanggan karena 1.000 koneksi bersamaan dapat membebani atau membuat API router
tidak responsif.

Ketentuan pemrosesan:
1. Gunakan satu antrean aktivasi khusus untuk MikroTik tersebut.
2. Hanya satu worker boleh memproses satu MikroTik pada waktu yang sama.
3. Worker membuka satu koneksi API dan menggunakan kembali koneksi itu untuk
   seluruh pelanggan dalam batch.
4. Proses sekitar 100-200 pelanggan per batch, sehingga 1.000 pelanggan dapat
   diselesaikan dalam sekitar 5-10 batch.
5. Periksa profil terlebih dahulu dan hanya ubah pelanggan yang masih EXPIRED.
6. Putus hanya sesi PPPoE pelanggan yang profilnya benar-benar berubah.
7. Berikan jeda kecil antarbatch jika penggunaan CPU/router atau respons API
   mulai melambat.
8. Simpan checkpoint pelanggan terakhir. Jika koneksi API terputus, worker
   melanjutkan dari pekerjaan pending dan tidak mengulangi pekerjaan success.
9. Pelanggan di akhir antrean dapat menunggu beberapa menit, tetapi proses
   tetap terkontrol dan tidak membanjiri MikroTik.
10. Mekanisme retry saat ini tetap menjadi pengaman, tetapi worker batch harus
    diterapkan sebelum menghadapi lonjakan 1.000 pembayaran pada satu router.
